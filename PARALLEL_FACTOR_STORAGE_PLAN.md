# Published parallel-factor storage and fallback training

The new isolated backend is `artifacts/upstream-parallel-mapped/source`. It inherits exactly the three-user-array storage implementation already verified for the serial temporal model (plus the unused daily array support), without changing the original parallel factor update code. The source remains pinned to49c9b3676e6bab90fdf77e9a2da984edbfe4fe5c. Qualifying training labels stay zero.

`upstream_parallel_mapped.py` passed24 configurations in each of four modes: heap/mapped storage with2/4 physical Rayon workers. Each compares initialization and20 epochs of every inner learned parameter/cache bit, scalar/grouped predictions and components, through16000 factors. The cases include1/16 logical chunks, both all-parallel training and the original sequential epochs1/10/20, plus cold users/items and unseen query dates. All final state signatures also match across storage modes and physical worker counts. The original public configuration literals are extracted directly from the pinned dispatcher. The dependency lock differs only by the direct declaration of the already-present libc package.

Evidence: `experiments/upstream-parallel-mapped/verification.json`, four native logs, and dependency-lock-verification.json. New source preparation and patch are under the candidate artifacts directory. The original serial backing-file persistence proof remains bound by hash. This establishes numerical compatibility on a small corpus at full factor widths. It does not establish full-corpus memory feasibility or prediction quality.

The public parallel presets use low_memory=true: they have no daily factor/cache matrices. Their large user-factor/cache matrices can be mapped, but item-frequency parameters and logical-chunk gradient buffers still occupy heap memory. The static allocation audit is `experiments/full-upstream-reproduction/parallel-capacity-audit.json`. In particular, the4000-factor original heap recipe has30.73GiB of core arrays alone; larger widths still need separate resource validation. No smaller rank is substituted for those jobs.

`upstream_parallel_fullscale.py` is queued for the original `tsvdx4p-1000lm` recipe, an independently named public model:1000 factors,20 epochs in each original trainx/ProbeX and fulltrain/qual phase,16 logical chunks and4 physical workers. It waits for a first frozen qualifying miss, skips if either current production attempt has already passed, and requires no more than12GiB of other registered native/model-fitter RSS plus40GiB free disk before starting. It runs in its own prediction tree under an exclusive lock and preserves partial outputs/mappings on failure. Both native phases and all verified output hashes are required for a completion receipt. This is an additional fresh model, not a completed blend or a target-score claim.

The resource guard samples actual owned/native/fitter RSS and disk while the job runs. Only a completed full-data run will supply resource evidence for this preset. The current85-column production path and conditional91-column fit/replay/audit path remain unchanged. Incorporating the1000-factor outputs into another blend will require a new frozen development/production recipe selected on known ProbeX only.

Do not edit these queued source files or the source preparation/verification they bind. Current full-data fits are not interrupted by this fallback. Reports: `experiments/upstream-parallel-fullscale/`; receipt: `artifacts/upstream-parallel-mapped/receipts/tsvdx4p-1000lm.json` once complete.
