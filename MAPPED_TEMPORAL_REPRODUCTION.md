# Original-capacity temporal models on 32 GiB

The published temporal recipes exceed this machine's RAM because they allocate dense user/day matrices. The candidate backend changes their storage and prediction cache, while keeping factor counts, initialization draws, learning rates, training order, epochs, and gradient arithmetic.

`upstream_mapped_prepare.py` creates a separate checkout at the pinned upstream commit. Its `StorageMatrix` owns either a stable heap allocation or a shared file mapping. Mutable views stay borrowed from their owner; a mutable reference to the stored static view is never exposed. File mappings flush and advise eviction in batches. Each mapping has a process-specific, exclusively created filename and is removed on ordinary destruction. Interrupted runs preserve their files for inspection.

The candidate uses upstream's existing lazy per-day cache instead of materializing a second giant day matrix. An explicit readiness flag preserves the original zero cache before the first epoch; without it the source lazy path produces different initialization predictions. This was caught by the parity tests and corrected before production training. Parameters remain freshly trained. The original training checkout is unchanged.

`upstream_mapped_verify.py` builds the candidate and compares it with an untouched copy of the pinned temporal implementation in the same executable. Four execution modes cover heap/mapped storage and materialized/lazy cache. Each mode checks 288 configurations across factors 0, 1, 6, 17, 60, 150, 400, 1200 and 4800; low-memory/full-day terms; implicit-feedback variants; ordinal/scalar heads; both historical gradient modes; and neighbor sampling settings. Initialization and five epochs must match bit for bit in parameters, row predictions, user-grouped predictions and component scores. A separate 72 MB matrix test checks RNG order and persistence after flush/eviction. This validates arithmetic on synthetic data; it does not establish full-scale runtime or score.

`upstream_mapped_job.py` requires a passing proof bound to the current generated source, support files, patch and executable. It binds the qualifying zero sentinel and native data paths, checks that the job dispatcher and pipeline are unchanged, and executes the original serial recipe in a separate prediction tree. Model receipts disclose the storage patch, proof and binary hashes. They are never described as an unmodified native binary.

Mapped jobs may run alongside the sequential native queue because they write to separate directories. They never copy outputs into the original wrapper's directory during its whole-directory receipt scan. The mapped worker watches both process groups' memory, disk space and its own memory; resource guards stop only its owned process group and retain incomplete output. Start with `tsvdx5-150o` to regenerate the missing ProbeX snapshots and fulltrain/qual predictions. Subsequent dependent jobs require explicit verified artifact integration, not unreceipted copying.

The overall target remains recovered qualifying RMSE below 0.85725 on both groups. No qualifying audit is performed by these scripts.
